# Repository AI guidance template

Use this structure in every repository `AGENTS.md`. Keep the shared sections
consistent and append repository-specific rules at the end. The blocks between
markers are generated by `infra/scripts/agents/sync-agents.sh`; do not edit them
by hand.

## Start here

- Read `README.md`.
- Read `docs/README.md`.
- Search open Gitea issues before starting.

<!-- begin operating-model -->
## Operating model

- Agents operate as `bot-event`; never as `human` or root.
- Code and documentation changes go through a branch and a pull request.
- Do not push directly to `main`.
- One open pull request per repository. The count includes every author and
  draft.
- While a PR is open, improve the existing issue or PR with comments and
  details, or push fixes to its head.
- Do not open another PR or push a new branch in that repository.
- Keep the PR within the repository size budget. If the change is larger, file
  a follow-up issue instead of appending it.
- If the work is urgent, ask `human` to merge the open PR first.
- After merge: delete the branch, fetch `main`, and start fresh.
- After close: write a restart note, delete the branch, and start fresh.
- Do not approve, dismiss, or merge pull requests. `human` performs review,
  approval, and merge in the Gitea UI.
- Do not create, edit, close, or comment on issues through the API on
  `human`'s behalf. Issue management belongs to `human`; agents may draft
  issue text and hand it back.
- Do not use admin tokens or bypass review.
- If a task requires a human-only action, stop and report.
- If the current user is not `bot-event`, stop before changing files.
- Never put credentials, tokens, or private data in commands, logs, PRs, or issues.
<!-- end operating-model -->

<!-- begin issue-workflow -->
## Issue tracker

Gitea issues are the only active work tracker. `docs/issues/` is retired and
must not receive new records.

- Before starting, search this repository's open Gitea issues.
- Capture evidence before opening an issue: `docs/repository/problem-intake.md`.
- Prefer an issue in the project board's `Ready` column. If no board exists,
  prefer a pinned issue. If none fits, create one.
- Labels: `bug`, `documentation`, `enhancement`. `question` is retired; triage
  a question into one of the three.
- Status lives on the Gitea project board, not in labels.
- Group work with milestones; do not add priority or area labels.
- Rank issues in the title with a type prefix: `3.x - Title` for bugs, `2.x`
  for documentation, `1.x` for features and ideas. Higher fraction = more
  important; reverse sort is the queue. Lower type runs after higher type.
- Ranks are decimal fractions, not versions: no trailing zeros (`3.1`, not
  `3.10`), no `0.x`, no `4.x`, up to 6 decimals, unique per repository.
- Minimal body requirements per type are in
  `ops/templates/docs/repository/issues.md`.
- `next-issue` selects the highest unblocked rank; do not use AI to pick the
  issue.
- Limits live in `ops/templates/docs/repository/limits.md`: 100 open issues,
  40 issue comments, 20 agent issue comments, 20 PR comments, 8 agent PR
  comments, 3 change-request rounds, 2 failed PRs per issue, and 10 merged
  slices per issue.
- A migration uses a chain of slice PRs. Non-final slices use `Part of #N`; the
  final slice uses `Closes #N`.
- A repo may keep one documented exception; see
  `ops/templates/docs/repository/labels.md`.
- Body sections:
  - required: Summary, Context, Expected outcome, Out of scope, Acceptance
    criteria, Plan, Decisions, Validation, References.
  - operations: Operational impact, Rollback, Problems encountered, Follow-ups,
    Definition of done.
- Use the operations sections when the change touches runtime, backups, secrets,
  data deletion, CI, or tags.
- No parent/child issue hierarchy. Link related issues with `#number`.
- Blocked work: name the blocker in a comment; `human` moves the board
  column.
- `bot-event` may create issues and comment. It must not edit, close, reopen,
  relabel, assign, or delete an existing issue. Comment "ready to close" and
  hand off.
- `bot-event` may edit or delete files only inside a branch, and must call out
  deletions in the PR body. It must not force-push, delete remote branches or
  tags, approve, or merge.
- `human` owns issue lifecycle, labels after creation, review, approval,
  merge, tags, repositories, tokens, and system changes.
- Prefer the `gitea-api` helper for Gitea actions; do not bypass it with raw
  `curl`.
- When a pull request deletes files, add a `## Deletions` section to the pull
  request body.
- Request review from `human`; never merge.
- While a PR is open, add details or comments to the existing issue or PR. Do
  not open another PR or a new branch in that repository.
- Merge the oldest open PR first; a newer PR must not merge while an older one
  is open.
- If the PR exceeds the size budget, stop appending. File a follow-up issue for
  the remaining scope.
- If the PR is abandoned, comment with a restart note and ask `human` to close
  it.
- Branch and PR: reference the issue (`Closes #N`); record decisions in the
  issue; `human` closes it when the PR merges.
- Issues inherit repository visibility. Never put credentials, tokens, private
  data, or unredacted logs in an issue.

## Repository tree

- Each repository is an independent tree.
- Do not add cross-repository links.
- Only `README.md` files may link to files in their own subtree.
- Do not link to parents or siblings; navigate up instead.
- Other Markdown files use plain text names, not links.
- Prefer search over a web of links.

<!-- begin decision-records -->
## Decision records

- Before answering a recurring question, read `docs/decisions/README.md`.
- Then read the linked ADRs, open and closed Gitea issues, and global ADRs in
  `ops/templates`.
- Active discussion stays in Gitea issues.
- Write an ADR when a decision is durable, repeated, cross-repository,
  security-related, or expensive to reverse.
- Global decisions live in `ops/templates/docs/decisions`; link them; do not copy.
- Pull requests are authored by `bot-event` and reviewed and merged by `human`.

- Read the current repo first.
- Read direct dependency AGENTS before changing an interface.
- Read consumer AGENTS before changing a shared schema or public API.
- Read transitive dependencies only when the change reaches them.
- Read the relevant global ADR/process in `ops/templates`.
- Stop on human-only actions.

<!-- begin knowledge-mode -->
## Knowledge mode

Declare the repository's knowledge mode in `infra/config/repo.json`:

- `observer` — broad, fuzzy, exploratory signals. One per ecosystem; requires a
  source list and a priority queue.
- `instrument` — fixed sources, measured data, high accuracy. AI must not be in
  the data path.
- `domain-audit` — repository knowledge compared to a domain model. Requires a
  coverage map and an AI loop.
- `mirror` — read-only copy of an upstream repository.

Rules:

- Observers never claim accuracy; promoted items leave the repository
  explicitly.
- Instruments fail closed on stale, missing, or inconsistent data.
- Domain audits draft issues; they never file or edit.
- Private repositories use local-only models.
- The mode is part of the repository contract; change it with an ADR.
<!-- end knowledge-mode -->

<!-- begin coverage -->
## Coverage

Domain-audit repositories keep a coverage map at `src/data/coverage.json` and a
human view at `docs/coverage.md`.

- One row per topic.
- Status: `covered`, `partial`, `missing`, or `stale`.
- `covered` and `partial` require a `ref`.
- Review rows when the domain changes or a model upgrade reveals a gap.
- The coverage map is the durable counterpart to the model's knowledge.
- The schema is `infra/config/coverage.schema.json`; run
  `infra/scripts/ci/validate-coverage.sh`.
<!-- end coverage -->

<!-- begin local-issues -->
## Local work records

- Agent work is tracked in `docs/issues/`, not in new native issues.
- Use `3.x` for bugs, `2.x` for documentation and chores, and `1.x` for
  features and code refactors. Higher fraction = more important.
- Filename: `<rank>-<slug>.json`; no trailing zero; one to six fractional digits.
- Exactly zero or one file may have `status: active`.
- Only the active file gets a native issue. Record `platform_issue_id` and
  `platform_issue_url` in it.
- A PR references the active file and closes the native issue:
  `Local-Issue: docs/issues/<file>.json` and `Closes #N`.
- On a failed PR, append an attempt locally, post the same summary on the native
  issue, close the PR, and keep the local file.
- On merge, delete the local file; the native issue closes through `Closes #N`.
- Native issues get one core label: `bug`, `documentation`, or `enhancement`.
  Keep security and area classification in local `tags`.
- Do not create extra native issues for agent work.
<!-- end local-issues -->

<!-- begin self-improvement -->
## Self-improvement loop

Domain-audit repositories run a bounded audit:

- Inputs: README, AGENTS, docs index, file tree, open issues, and the coverage
  map.
- Roles: auditor, critic, and planner.
- Output: a report outside git and at most five issue drafts.
- Human review; `bot-event` files selected drafts.
- No auto-filing, no repository edits, and no web facts.
- Private repositories use local models only.
- Cadence: weekly for active repositories, monthly for stable ones.
- A model upgrade is a trigger to rerun the audit.
<!-- end self-improvement -->

## Shared rules

- Do not create `docs/wishlist/`, `docs/problems/`, or `docs/questions/`.
- Put every `.sh` file under `infra/scripts/`.
- Put every Dockerfile under `infra/docker/`.
- Keep `infra/config/repo.json` authoritative.
- Prefer free managed services with the largest user base.
- Prefer Gitea; GitHub, GitLab, and Bitbucket are upload-only mirrors.
- Use Docker locally and in cloud deployment.
- Do not add paid infrastructure to the default path.
- Do not add editor or devcontainer configuration.
- Open a question only for material dependency, data-model, platform, security,
  or expensive migration choices.
- Use Git tags; do not publish release artifacts without an issue.
- Define input, output, rates, retention, and the bottleneck before choosing
  a database, queue, or major dependency.

<!-- begin scripts -->
## Scripts

- `infra/scripts/ci/` is read-only. CI may execute it.
- `infra/scripts/manual/` writes files. CI must never execute it.
- A write helper is run manually while preparing a PR, not by CI.
- Validators accept `--root`, read only, and exit non-zero with the exact path.
- `ci.sh` calls `ci/all.sh`; `ci/all.sh` runs every `ci/validate-*.sh`.
- Do not add a write helper unless a manual step is genuinely required.
- Every write helper documents what it changes and how to check the diff.
- PRs contain the file changes; no bot commits and no auto-fixes.
- A manual workflow must be `workflow_dispatch` and must open a branch + PR,
  never push to `main`.
